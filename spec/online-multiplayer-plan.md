# 在线联机规划

## 1. 目标与边界

在线联机是人机版本之后的正式阶段。离线基础已经完成，私人房间、在线 AI、完整 65 格奥普港和现有表现队列均已接入独立游戏服务；后续可靠性工作继续沿用共享规则内核、可序列化协议和可替换 authority，不重写玩法。

首个联机版本目标：

- 通过房间码创建或加入私人房间。
- 支持 2 至 4 个座位，允许真人与 AI 混合占位。
- 房主选择地图、规则集和是否使用 AI 补位，所有人准备后开始。
- 服务端权威处理骰子、起始道具候选抽取、事件抽取、移动、碰撞和胜负。
- 支持刷新页面和短时断线后的状态恢复。

首个联机版本不包含账号、好友、公开匹配、排行榜、观战、语音或跨局成长。

## 2. 推荐拓扑

```text
Browser Client
  ├─ Static HTTPS: React + Vite assets
  ├─ HTTPS ─► Game Server: auth / create / join / room metadata
  └─ WSS   ─► Game Server: commands / snapshots / events / presence
                         │
                         ▼
              Session Gateway (TypeScript)
                         │
                         ▼
                Room Session Authority
                  │             │
                  ▼             ▼
           Shared Game Core   Snapshot Store
```

- Web 客户端使用 React + Vite + TypeScript，构建为静态资源。
- 游戏服务端是独立 Node.js + TypeScript 常驻服务，与浏览器共享规则和协议类型。
- 游戏服务端的 HTTP 接口只处理建房、入房和恢复凭证；进入房间后使用 WebSocket 双向通信。
- 协议第一版使用经过运行时校验的 JSON，暂不引入二进制协议。
- 每个房间对应一个顺序处理命令的 session actor，避免同一回合并发写入。
- 本地人机版的 `LocalAuthority` 与服务端 `RoomAuthority` 调用同一个纯规则包。

具体 HTTP/WebSocket 库和部署平台在技术验证阶段确定，不写进规则内核。

### 2.1 Web 与服务端边界

Vite 只构建浏览器静态资源，不提供生产后端运行时。账号、登录、房间 HTTP API、WebSocket、在线 AI 和权威状态都属于独立 Node.js 游戏服务。

离线人机模式不请求后端；在线模式通过配置的 HTTPS/WSS 地址连接服务。前端静态资源和游戏服务可以独立部署、缓存、扩缩容和回滚，但同一个房间只能有一个权威状态源。

## 3. 代码与包边界

进入联机实施前，工程建议整理为：

```text
apps/
  web/                 React + Vite + PixiJS 客户端
  game-server/         独立 Node.js 房间、连接与权威会话
packages/
  game-core/           纯规则、随机数、地图与内容定义
  game-ai/             浏览器与服务端共享的 AI 决策
  game-protocol/       命令、快照、事件与运行时校验
  game-content/        版本化事件、道具、地图和规则集
```

`game-core` 不依赖 React、PixiJS、WebSocket、数据库或 Node.js 专用 API。`game-protocol` 不导出显示对象，只传输 JSON 可表达的数据。

## 4. 房间与身份

- 创建房间后返回短房间码、`gameId` 和一次性恢复凭证。
- 首版使用游客显示名，不要求注册账号。
- 每个连接绑定稳定 `playerId` 和座位；刷新页面后通过恢复凭证重新绑定。
- 房主可以切换空座位为 AI、移除未准备玩家并开始游戏。
- 开局后地图、规则集、内容版本和座位顺序锁定。
- 房主最后一条连接断开后进入 30 秒宽限期；宽限期内权限不变，超时后转移给最早加入且在线的真人。

## 5. 权威命令流程

1. 客户端提交包含 `commandId`、`playerId` 和 `expectedRevision` 的 `CommandEnvelope`。
2. 服务端校验房间、座位、行动权、命令合法性和 revision。
3. 服务端规则内核产生随机结果并原子提交新状态。
4. 房间 revision 递增，服务端向所有客户端广播领域事件和最新摘要。
5. 每个客户端独立播放 `PresentationCue`；动画速度不会影响服务端回合。
6. 重复 `commandId` 返回之前的结果，过期 revision 返回重同步响应。

客户端永远不能提交骰子点数、抽中的事件或最终位置。服务端也不接收“动画完成”作为规则推进条件。

## 6. 同步与断线恢复

- 单实例服务将大厅状态、最新权威检查点和已处理命令结果写入 SQLite；每次大厅变更和 authority 更新后同步落盘。
- 设置 `DATABASE_URL` 后改用 PostgreSQL 共享存储；房间行保存 owner、租约到期时间和单调递增 fencing token，非 owner 实例只返回当前 `ownerUrl`，不会创建第二份 authority。
- 真人玩家最后一条连接断开后保留座位，并进入默认 30 秒重连宽限期；多标签页只关闭一条连接不会标记离线。
- 宽限期内恢复会取消倒计时并保留原房主；房主超时后按座位顺序转给最早加入且在线的真人，AI 不接管房主。
- 重连时服务端发送按本人裁剪的最新完整快照和最新合法命令，不补发断线期间的旧表现事件。
- 客户端应用快照后清空待播放队列，重建 React UI 和 PixiJS 棋子位置，跳过旧骰子、路线和道具动画。
- 服务进程重启后读取未过期房间并重建 authority；真人成员重新进入 30 秒宽限，恢复连接直接收到最新投影快照，不补播旧表现。

## 7. 一致性与安全

- 所有随机数只在权威端产生，并记录种子、游标和结果。
- 服务端按房间串行处理命令，authority 更新和完整同步都必须在带 fencing token 的持久化成功后才对客户端可见。
- 每个协议消息都校验类型、尺寸、版本和发送频率。
- 客户端只接收当前房间可见的信息，不广播恢复凭证或内部随机状态。
- `rulesetVersion`、`contentVersion` 或协议版本不一致时拒绝开始，而不是尝试静默兼容。
- 对局日志需要足以重放争议局，但不记录聊天、凭证或其他敏感信息。

## 8. 分阶段实施

### 阶段 0：离线基础

- 完成 `1v1`、`1v2`、`1v3` 人机模式。
- 提取纯规则内核、`GameAuthorityPort` 和三种控制器接口。
- 完成命令、快照、事件的 JSON 往返、固定种子和恢复测试。

### 阶段 1：本地联机技术样片

- [x] 启动单进程 TypeScript 服务和内存房间。
- [x] 两个浏览器窗口通过房间码进入 8 格最小地图对局。
- [x] 验证重复命令、旧 revision 拒绝、刷新重连和不依赖动画的即时状态应用。

当前实现位于 `apps/game-server`。准备页使用昵称与棋子外观创建或加入房间；服务端按房间串行处理命令，并通过 WebSocket 发送按玩家裁剪的快照和合法命令。技术样片已经扩展为 2 至 4 个座位的私人大厅及完整 65 格奥普港对局，第二名玩家加入后不会自动开局。房主可以调整容量、添加或移除 AI，并在所有成员准备后手动开始；在线 AI 使用共享 `game-ai` 策略在服务端自动行动。在线 Web 复用 PixiJS `BoardScene`、Three.js 双骰、道具撕裂和暂停沙漏表现，权威快照立即接收，HUD 与行动者在表现队列完成后更新。协议 v12 延续 v11 的 owner 路由，并在房间状态中公开锁定的 `contentVersion`、`mapVersion` 和 `rulesetVersion`；客户端按房间保存 owner 地址，遇到非所有者实例或租约迁移时自动改连。恢复凭证明文仅保存在当前标签页的 `sessionStorage`，服务端只持久化 SHA-256 摘要。游戏服务器创建房间时读取当前不可变运行时内容包，持久化版本标识，并在重启恢复时按历史版本精确加载，因此后续发布或回滚不会改变已有房间的规则内容。玩家 Web 使用恢复凭证从 owner 读取一次锁定定义，校验房间与快照版本后渲染地图、事件、道具和皮肤；内容接口不暴露机器令牌或其他地图版本。

### 阶段 2：私人房间 MVP

- [x] 扩展到 2 至 4 个座位，加入准备状态、AI 补位和房主手动开始。
- [x] 对大厅命令实施房主权限、容量和开局状态校验，并由服务端串行驱动在线 AI。
- [x] 将完整 65 格奥普港和现有 PixiJS 表现队列接入在线 authority。
- [x] 加入 30 秒断线宽限、座位保留、房主超时转移与大厅/对局连接倒计时。
- [x] 持久化每次大厅变更与权威更新，使服务重启后仍可恢复房间、对局和重复命令结果。
- [x] 完成跨浏览器与高延迟测试后发布邀请制版本。

在线发布门禁由 `apps/web/e2e/online-release.spec.ts` 和根 Playwright 配置承载：测试同时启动独立内存游戏服与 Vite，Chromium、Firefox、WebKit 均覆盖双客户端建房、加入、准备、开局和刷新后的座位恢复；高延迟场景注入 250ms 单向 WebSocket 延迟、重复权威帧和重复游戏命令，验证 `revision` 保持单调且客户端不中断。CI 串行执行三种内核，避免软件渲染器并发争用。

### 阶段 3：可靠性与部署

- [x] 将单实例活跃房间租约和恢复数据放入 SQLite，并增加进程重启恢复。
- [x] 增加监控、限流、协议指标和异常对局诊断。

当前基础实现位于 `apps/game-server`：`/health` 返回协议版本、进程运行时间和房间汇总，`/metrics` 提供 Prometheus 文本指标；建房/入房、WebSocket 升级和单连接消息分别使用令牌桶限流，超限返回 `429` 或关闭连接并携带重试提示。服务端记录规范化 HTTP、协议、命令、限流和诊断计数；结构化异常日志只包含请求号、房间号、游戏号、命令类型、revision、阶段和错误码，不记录恢复凭证、原始载荷或随机内部状态。反向代理来源只有在显式设置 `TRUST_PROXY=true` 时才读取 `X-Forwarded-For`。

- [x] 通过 PostgreSQL 共享租约、owner 路由和 fencing token 支持多实例房间分片，保证同一房间始终只有一个可写 authority。

共享模式通过 `DATABASE_URL` 启用，并要求设置 `INSTANCE_URL` 或 `PUBLIC_SERVER_URL` 为客户端可访问的 HTTP(S) 地址。`INSTANCE_ID` 可显式提供，默认每个进程生成随机 ID；`ROOM_LEASE_DURATION_MS` 和 `ROOM_LEASE_RENEW_INTERVAL_MS` 默认分别为 15000 与 5000，续租间隔必须短于租约。未设置 `DATABASE_URL` 时继续使用 `ROOM_DB_PATH` 指定的 SQLite，明确仅支持单实例。

### 阶段 4：可选平台能力

- 账号、好友邀请、公开匹配、观战和排行榜分别立项。
- 这些能力不得引入角色养成，也不得改变已有对局协议的权威原则。

## 9. 联机 MVP 验收标准

- 2、3、4 名参与者及真人/AI 混合座位都能完成完整对局。
- 同一种子和命令序列在本地 authority 与服务端 authority 上得到相同结果。
- 延迟、重复和乱序消息不会造成重复投骰、重复移动或重复结算。
- 任一客户端刷新或短时断线后能恢复正确座位、棋子位置、道具、轮次和待操作状态。
- 一个客户端动画失败、失焦或掉线不会阻塞其他客户端的权威状态。
- 服务器拒绝非当前行动者、伪造骰子结果和版本不兼容的命令。
