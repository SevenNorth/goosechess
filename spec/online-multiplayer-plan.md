# 在线联机规划

## 1. 目标与边界

在线联机是人机版本之后的正式阶段，不在当前首版中实现。当前代码仍需先建立共享规则内核、可序列化协议和可替换 authority，确保联机阶段不重写玩法。

首个联机版本目标：

- 通过房间码创建或加入私人房间。
- 支持 2 至 4 个座位，允许真人与 AI 混合占位。
- 房主选择地图、规则集和是否使用 AI 补位，所有人准备后开始。
- 服务端权威处理骰子、事件抽取、移动、碰撞和胜负。
- 支持刷新页面和短时断线后的状态恢复。

首个联机版本不包含账号、好友、公开匹配、排行榜、观战、语音或跨局成长。

## 2. 推荐拓扑

```text
Browser Client
  ├─ HTTPS ─► Next.js: pages / auth callback / optional BFF
  ├─ HTTPS ─► Game Server: create / join / room metadata
  └─ WSS   ─► Game Server: commands / snapshots / events / presence
                         │
                         ▼
              Session Gateway (TypeScript)
                         │
                         ▼
                Room Session Authority
                  │             │
                  ▼             ▼
           Shared Game Core   Snapshot Store
```

- Web 客户端使用 Next.js App Router + React + TypeScript。
- 游戏服务端是独立 Node.js + TypeScript 常驻服务，与浏览器共享规则和协议类型。
- 游戏服务端的 HTTP 接口只处理建房、入房和恢复凭证；进入房间后使用 WebSocket 双向通信。
- 协议第一版使用经过运行时校验的 JSON，暂不引入二进制协议。
- 每个房间对应一个顺序处理命令的 session actor，避免同一回合并发写入。
- 本地人机版的 `LocalAuthority` 与服务端 `RoomAuthority` 调用同一个纯规则包。

具体 HTTP/WebSocket 库和部署平台在技术验证阶段确定，不写进规则内核。

### 2.1 为什么不直接使用 Next.js 游戏后端

Next.js 的 Route Handlers、Server Actions 和服务端组件本身就是后端能力，可以用于登录、Cookie、普通 CRUD API 和页面数据加载。它不是“只能做前端”。

权威游戏会话需要长期 WebSocket、持续房间内存、顺序命令队列、在线 AI 和精确的重连生命周期。即使自托管 Next.js 可以挂载这些功能，也会让页面服务与游戏房间只能一起扩缩容和重启；部署到无状态函数平台时风险更明显。

因此正式边界是：Next.js 负责 Web 产品层，独立 Node.js 服务负责实时游戏层。两者可以共享认证信息和 TypeScript 包，但不能同时成为对局状态源。

## 3. 代码与包边界

进入联机实施前，工程建议整理为：

```text
apps/
  web/                 Next.js + React + PixiJS 客户端
  game-server/         独立 Node.js 房间、连接与权威会话
packages/
  game-core/           纯规则、随机数、地图与内容定义
  game-protocol/       命令、快照、事件与运行时校验
  game-content/        版本化事件、道具、地图和规则集
```

`game-core` 不依赖 React、PixiJS、WebSocket、数据库或 Node.js 专用 API。`game-protocol` 不导出显示对象，只传输 JSON 可表达的数据。

## 4. 房间与身份

- 创建房间后返回短房间码、`gameId` 和一次性恢复凭证。
- 首版使用游客显示名，不要求注册账号。
- 每个连接绑定稳定 `playerId` 和座位；刷新页面后通过恢复凭证重新绑定。
- 房主可以切换空座位为 AI、移除未准备玩家并开始游戏。
- 开局后地图、规则集、内容版本和座位顺序锁定。
- 房主离开不改变规则状态；房主权限转移给最早加入的在线真人。

## 5. 权威命令流程

1. 客户端提交包含 `commandId`、`playerId` 和 `expectedRevision` 的 `CommandEnvelope`。
2. 服务端校验房间、座位、行动权、命令合法性和 revision。
3. 服务端规则内核产生随机结果并原子提交新状态。
4. 房间 revision 递增，服务端向所有客户端广播领域事件和最新摘要。
5. 每个客户端独立播放 `PresentationCue`；动画速度不会影响服务端回合。
6. 重复 `commandId` 返回之前的结果，过期 revision 返回重同步响应。

客户端永远不能提交骰子点数、抽中的事件或最终位置。服务端也不接收“动画完成”作为规则推进条件。

## 6. 同步与断线恢复

- 服务端保留周期性 `GameSnapshot` 和之后的有序领域事件。
- 客户端记录最后确认的 `revision` 与表现提示序号。
- 短时断线重连时，服务端发送缺失事件；差距过大或版本不匹配时发送完整快照。
- 客户端应用快照后重建 React UI 和 PixiJS 棋子位置，并跳过已经确认的旧动画。
- 玩家掉线时先保留座位并暂停其输入计时；超时后可按房间设置等待、交给 AI 或退出。默认策略在联机可玩测试后确定。
- 服务进程重启恢复属于持久化阶段；早期技术样片只保证连接级重连。

## 7. 一致性与安全

- 所有随机数只在权威端产生，并记录种子、游标和结果。
- 服务端按房间串行处理命令，提交状态与事件日志必须是一个原子操作。
- 每个协议消息都校验类型、尺寸、版本和发送频率。
- 客户端只接收当前房间可见的信息，不广播恢复凭证或内部随机状态。
- `rulesetVersion`、`contentVersion` 或协议版本不一致时拒绝开始，而不是尝试静默兼容。
- 对局日志需要足以重放争议局，但不记录聊天、凭证或其他敏感信息。

## 8. 分阶段实施

### 阶段 0：离线基础

- 完成 `1v1`、`1v2`、`1v3` 人机模式。
- 提取纯规则内核、`GameAuthorityPort` 和三种控制器接口。
- 完成命令、快照、事件的 JSON 往返、固定种子和恢复测试。

### 阶段 1：本地联机技术样片

- 启动单进程 TypeScript 服务和内存房间。
- 两个浏览器窗口通过房间码完成一局最小地图对局。
- 验证重复命令、乱序命令、刷新重连和动画快进。

### 阶段 2：私人房间 MVP

- 扩展到 2 至 4 个座位和完整 65 格地图。
- 加入准备状态、AI 补位、房主转移、超时与明确的连接提示。
- 保存周期快照，使短时断线不丢失对局。
- 完成跨浏览器与高延迟测试后发布邀请制版本。

### 阶段 3：可靠性与部署

- 将活跃房间租约和恢复数据放入持久化存储。
- 增加进程重启恢复、监控、限流、协议指标和异常对局诊断。
- 通过房间分片支持多实例部署，保证同一房间始终只有一个 authority。

### 阶段 4：可选平台能力

- 账号、好友邀请、公开匹配、观战和排行榜分别立项。
- 这些能力不得引入角色养成，也不得改变已有对局协议的权威原则。

## 9. 联机 MVP 验收标准

- 2、3、4 名参与者及真人/AI 混合座位都能完成完整对局。
- 同一种子和命令序列在本地 authority 与服务端 authority 上得到相同结果。
- 延迟、重复和乱序消息不会造成重复投骰、重复移动或重复结算。
- 任一客户端刷新或短时断线后能恢复正确座位、棋子位置、道具、轮次和待操作状态。
- 一个客户端动画失败、失焦或掉线不会阻塞其他客户端的权威状态。
- 服务器拒绝非当前行动者、伪造骰子结果和版本不兼容的命令。
