# 管理员内容平台规划

## 1. 目标与边界

管理员内容平台统一承载地图、事件和棋子皮肤的制作、校验、预览、审核与发布。
它是独立的运营工具，不放入公开游戏客户端，也不开放玩家自制内容。

平台首期目标：

- 管理员和内容编辑可以创建草稿，不直接修改已发布内容。
- 地图、事件和皮肤共用版本、审核、发布、回滚和审计能力。
- 发布生成不可修改的 `contentVersion`；进行中的房间继续使用开局时锁定的版本。
- 游戏客户端只读取已发布内容，不能访问草稿、上传接口或管理 API。

## 2. 工程位置

```text
apps/
  web/             玩家游戏客户端
  admin/           管理后台
  game-server/     房间与权威对局
  content-server/  草稿、资源、审核和发布 API

packages/
  game-content/    内容类型、运行时读取和内置默认内容
  content-tools/   校验、编译、版本生成、导入与导出
```

- `apps/admin` 使用独立入口、构建产物和部署权限，不与玩家页面共用路由权限。
- `apps/content-server` 保存草稿、修订、审核记录和发布记录，并调用对象存储保存图片及生成资源。
- `packages/game-content` 保持可在浏览器与 Node.js 运行，不依赖数据库或管理页面。
- `packages/content-tools` 提供纯函数校验、内容包编译、哈希和迁移工具。

## 3. 账号与权限

后台实施前只需要最小账号与角色权限，不要求同时完成好友、公开匹配或排行榜。

- `player`：只能使用玩家客户端和已发布内容。
- `content-editor`：可以创建和修改地图、事件草稿以及运行预览校验。
- `admin`：可以上传皮肤、审核、发布、下架和回滚内容版本。

服务端必须在每个管理 API 上校验身份和角色；前端隐藏菜单不能作为权限控制。

## 4. 内容生命周期

```text
草稿 → 自动校验 → 游戏内预览 → 提交审核 → 管理员发布 → 不可变内容版本
```

- 草稿允许多次保存，并使用修订号处理并发编辑。
- 自动校验失败时禁止提交审核；审核未通过时返回草稿并记录原因。
- 发布必须原子生成内容清单、资源清单、版本号和哈希。
- 已发布版本不能原地覆盖；修复必须创建新版本。
- 回滚表示让新房间重新指向旧版本，不删除历史内容包。
- 房间创建后锁定 `contentVersion`、规则集版本和地图版本。

## 5. 事件编辑器

事件编辑器负责：

- 标题、说明、分类、视觉色调和 AI 评分。
- 常规效果、骰子检定门槛、成功效果与失败效果。
- 一个或多个语义事件池的归属。事件池是独立、可版本化的内容定义，使用稳定 slug 作为 ID 和可修改的显示名；不得用地图地点 ID 充当事件池 ID。
- 效果参数的结构化表单，不允许管理员直接输入可执行代码。
- 单卡预览、三选一预览、固定种子结算和批量模拟。

发布校验至少覆盖 ID 唯一、文案完整、检定门槛可达、效果参数合法、引用存在，以及每个生效事件池至少包含三张有效卡牌。

事件池首期结构为 `id / name / eventIds`。池表达内容语义，例如“通用”“餐饮”“探索”“社交”，而不是某张地图上的具体建筑；同一语义池可以被多张地图、多个地点复用。事件可归属多个池，但发布包只保存一份事件定义。

## 6. 地图编辑器

地图编辑器使用可视化画布编辑，并将路径格与表现标记分开建模：

- 地图逻辑尺寸、纸张背景和资源清单。
- 有序路径、格子坐标、旋转、类型和格号。
- 起点、地点和终点标记的名称、贴图、关联格子、坐标、缩放和旋转。
- 只有 `location` 标记可以关联一个语义事件池；`start` 与 `finish` 可以自定义名称和贴图，但禁止关联事件池。
- 新建地点不按事件池数组顺序自动归属；编辑者必须明确选择事件池，未选择时保留为草稿校验错误。
- 起点、普通事件格、地点事件格和胜利格；普通事件格直接引用语义事件池，默认可使用 `general`。
- 地图允许的事件池与道具白名单或黑名单。

画布至少提供“选择”“添加格子”“添加贴图”“平移”四种模式。添加贴图时先上传 PNG、JPEG 或 WebP 图片，再点击画布落点创建标记；新标记默认为不参与规则的装饰，随后可在属性面板将用途设为起点标识、地点或终点标识。点击空白区域按路径末尾新增格子；删除非起点格时必须连续重排后续格号，并同步胜利格、标记和旧地标引用。拖动格子只修改视觉坐标，不改变路径顺序；标记贴图可以独立拖动、缩放、旋转和调整透明度，属性检查器保留数字输入以便精确调整。撤销/重做、网格吸附和越界提示属于地图阶段的发布门禁。

地图编辑工作区采用左侧草稿列表、中央主画布和右侧点选属性面板。地图基础信息保留在中央顶部；格子与标记不使用常驻长列表，必须通过画布点选后在右侧编辑。胜利格不使用地图级逗号分隔输入；选中格子并将类型设为“终点”时，编辑器同步维护底层 `winningSpaceIds`，并允许规则需要的多个终点格。草稿或已驳回内容允许删除，审核中、已批准和已发布内容禁止删除；删除由服务端 RBAC 强制校验并写入审计记录。

奥普港默认地图必须在本次模型迁移中保持 0 至 65 的路径顺序、格子坐标、资源和胜利规则。迁移关系如下：

| 现有标记 | 新类型 | 事件池 |
|---|---|---|
| `repair-room` / 维修室 | `start` | 无 |
| `snack-stand` / 小吃摊 | `location` | `aup-food` |
| `scavenger-beach` / 拾荒沙滩 | `location` | `aup-exploration` |
| `sailors-home` / 水手之家 | `location` | `aup-sailors` |
| `yellow-dog` / 大黄狗 | `location` | `aup-yellow-dog` |
| `madhouse` / 疯人院 | `location` | `aup-madhouse` |
| `grand-boil` / 十全大煮 | `location` | `aup-cooking` |
| `mixologist` / 调饮师 | `location` | `aup-mixology` |
| `noise-house` / 喧声屋 | `finish` | 无 |

这些首期池保留现有事件分组以保证内容行为不变，但池 ID 已与地点 ID 解耦。后续经过内容审核可以把适合复用的卡牌迁入更通用的 `food / social / exploration` 等池，不在模型迁移时暗中改变抽卡概率。

预览页必须复用正式棋盘渲染和移动路径计算，支持固定种子模拟、折返、碰撞、地标覆盖及胜利区验证。发布前检查格子索引连续、坐标有效、地标引用一致、胜利格可达且至少存在一个胜利格。

## 7. 皮肤制作页面

管理员的必填操作只有上传一张原始图片和确认展示名，其余步骤由系统完成：

1. 校验文件格式、尺寸、文件体积、安全性和来源信息。
2. 检测明显水印、低分辨率、严重裁切和无法可靠处理的图片。
3. 生成透明背景、标准画布、锚点、阴影、缩略图和运行时纹理。
4. 生成稳定 `skinId`、`TokenSkinDefinition` 和资源清单。
5. 在桌面 HUD、准备页、棋盘和目标选择卡片中预览。
6. 管理员确认后进入统一内容审核与发布流程。

任一步失败都必须阻止发布并给出可读原因，不能静默生成低质量资源。皮肤只包含外观数据，不允许出现属性、技能、稀有度或成长字段。

## 8. 存储、安全与审计

- 关系数据库保存账号角色、草稿、修订、审核、发布和审计记录。
- 对象存储保存原图、处理中间产物和已发布资源；公开客户端只能读取已发布前缀。
- 上传使用文件签名检测、解码后尺寸限制和隔离处理，不能信任扩展名或浏览器 MIME。
- 日志记录操作者、时间、来源版本、变更摘要和发布结果，但不记录密码、会话令牌或房间恢复凭证。
- 删除草稿可以恢复；已发布版本和审计记录不能物理删除。

## 9. 实施顺序

1. 最小账号登录、会话和 `player/content-editor/admin` 角色校验。
2. 内容服务的草稿、修订、校验、审核、发布、回滚和审计基础。
3. 事件编辑器，先验证完整内容工作流。
4. 独立事件池、地图标记模型和奥普港兼容迁移。
5. 地图可视化编辑器及正式棋盘预览。
6. 皮肤上传、自动处理和审核页面。
7. 将当前 TypeScript 默认内容导入为第一个只读发布版本。

当前实施状态（2026-08-06）：步骤 1 至步骤 5 已完成，步骤 6 尚未开始。内容服务使用 SQLite 保存账号、草稿、修订、校验、审核、发布版本和审计；发布与回滚会原子生成经过完整定义校验的不可变运行时内容包，并提供当前和历史版本读取接口。`packages/content-tools` 提供结构校验、规范化 JSON、SHA-256 哈希、运行时内容组合以及旧地图到语义事件池/地图标记的显式迁移，固定种子回放确认迁移前后路径、抽卡和胜利规则不变。独立 `apps/admin` 已完成登录、会话恢复、角色守卫，以及事件草稿、结构化效果、事件池、单卡/三选一、固定种子模拟、审核、发布、版本和审计界面。地图工作台已支持完整草稿生命周期、格子和地图标记编辑、事件池、资源上传、核心地图校验、权威路径折返模拟及画布布点和变换；`packages/board-renderer` 统一玩家端与管理预览的背景、路径、格子和地图标记静态渲染。游戏服务器已在建房时锁定内容、地图和规则集版本，并在重启时加载精确历史版本；玩家 Web 使用恢复凭证读取、校验和缓存房间定义，地图、事件、道具和皮肤表现均使用锁定版本。皮肤制作页面尚未开始。

## 10. 验收标准

- 未登录用户和 `player` 无法访问管理页面或管理 API。
- 编辑草稿不会影响当前客户端、已有房间或已发布内容。
- 地图和事件可以只通过结构化表单完成编辑、校验、预览和发布。
- 管理员上传单张合格图片后，无需修改代码即可发布新皮肤。
- 发布失败不会产生客户端可见的半成品版本。
- 新房间可使用新版本，进行中房间保持原版本并能继续恢复。
- 所有发布和回滚操作都有可查询的审计记录。

## 11. 明确不包含

- 普通玩家上传地图、事件或皮肤。
- 脚本代码、任意表达式或插件在游戏服务器中执行。
- 皮肤属性、角色技能、等级、经验、装备或养成。
- 用后台项目替代玩家客户端中的地图预览页。
