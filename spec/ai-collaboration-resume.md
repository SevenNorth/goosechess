# 鹅了个棋｜简历项目经历

## 可直接使用版本

### 鹅了个棋｜AI 协作全栈多人联机 Web 游戏

**项目时间：** 2026.07 - 至今

**项目角色：** 独立开发 / 产品与架构设计 / AI 协作开发

**技术栈：** TypeScript、React、Vite、PixiJS、Three.js、XState、Node.js、WebSocket、Zod、SQLite、PostgreSQL、Docker、Vitest、Playwright

**项目简介：**

面向桌面浏览器的多人竞速棋盘游戏，支持 65 格地图、离线人机对战、2 至 4 人真人/AI 混合联机、事件与道具系统、断线恢复，以及地图、事件、皮肤的可视化内容管理。项目采用服务端权威架构，并通过规格驱动的 AI 协作流程完成需求拆解、实现、测试和文档维护。

**核心工作：**

- 设计 npm Workspaces Monorepo，将项目拆分为玩家端、游戏服务器、内容服务器、管理后台 4 个应用，以及规则、协议、AI、内容、渲染等 6 个共享包，明确领域逻辑、网络协议、视觉表现和内容生产的模块边界。
- 实现与 UI 解耦的纯函数规则引擎，以 `Command -> State + DomainEvent + PresentationCue` 统一驱动回合、骰子、移动、碰撞、事件、道具和胜负结算；使用固定种子与 RNG 游标保证随机过程可序列化、可恢复，并让离线、联机和 AI 复用同一套规则。
- 构建 Node.js + WebSocket 服务端权威联机架构，通过 `commandId` 缓存保证重复请求幂等，通过 `expectedRevision` 实现乐观并发控制；所有命令按房间串行执行，并由服务端校验玩家身份、行动权和合法操作，避免重复投骰、越权操作与状态覆盖。
- 将权威状态与动画表现分离：客户端收到消息后立即推进权威快照，再由 XState、PixiJS 和 Three.js 顺序播放骰子、路线、棋子移动及卡牌效果；动画失败或超时可直接同步至最新快照，不阻塞服务端和其他玩家。
- 实现 2 至 4 人私人房间、真人/AI 混合座位、准备与开局、30 秒断线宽限、刷新恢复、掉线 AI 接管和房主转移；服务端按玩家裁剪快照、私有事件和合法命令，避免泄露其他玩家道具、候选内容及权威随机状态。
- 设计可替换房间持久化端口：使用 SQLite WAL 支持单实例进程重启恢复，使用 PostgreSQL owner lease、路由和 fencing token 支持多实例房间分片，确保同一房间始终只有一个可写 Authority。
- 建设带认证与 RBAC 的内容管理平台，支持地图、事件和皮肤的编辑、校验、预览、审核、不可变版本发布与回滚；新房间使用当前版本，进行中的房间锁定开局内容版本，避免发布改变存量对局。
- 建立“规格先行、AI 辅助实现、自动化验收”的协作流程，通过产品/技术规格、仓库级约束、跨会话交接 Prompt、Git 小步提交和自动化检查限制 AI 修改范围，并由人工负责领域建模、架构取舍、安全边界和最终验收。

## 使用注意

- 不要写“AI 独立完成项目”，应强调自己负责需求、领域建模、架构、安全边界和验收，AI 用于检索、实现辅助、测试补充及文档同步。
- 不要写“实现分布式一致性”，更准确的表达是“通过 owner lease 和 fencing token 保证单房间单写者”。
- 不要写“事件溯源架构”。项目会产生领域事件，但当前主要恢复机制是权威快照与检查点，不是完整事件溯源。
- 截至 2026-08-11，当前全量单元/组件测试为 201 项中 196 项通过、5 项失败。修复并重新验证前，不要在简历中写“全部测试通过”或使用通过率作为成果。
