# 实施计划

## 1. 重写原则

当前 React DOM 版本保留为规则参考，不在其绝对定位棋盘上继续堆叠动画。新版本逐步替换渲染层，并优先建立可验证的规则内核和场景边界。

重写期间必须保持 `npm run dev` 可启动。较大的场景改造应通过功能开关接入，直到新棋盘达到可玩状态。

## 2. 里程碑 A：规则内核

目标：让游戏规则完全脱离 React。

工作内容：

- 建立 XState 回合状态机。
- 建立地图注册表和默认地图定义，规则层不得引用固定的 65 格常量。
- 将第 63、64、65 格配置为胜利落点，并覆盖普通移动、折返和事件移动的测试。
- 建立带种子的随机数服务。
- 建立 `2 至 4` 座位的参与者集合、座次推进与 `local / ai / remote` 控制器接口，默认局为四人。
- 定义可 JSON 序列化的 `GameCommand`、`GameSnapshot`、领域事件和表现提示。
- 建立 `GameAuthorityPort` 与浏览器内 `LocalAuthority`，确保以后可替换为服务器权威端。
- 将移动、折返、碰撞、暂停和胜负判断改为纯函数。
- 迁移当前事件与道具配置。
- 为所有规则建立单元测试。
- 增加自动模拟对局入口。
- 使用一张不同格数的测试地图验证地图扩展接口。
- 验证切换棋子 `skinId` 不会改变任何规则结果。
- 验证规则快照不包含 XState actor、DOM、PixiJS、计时器或音频对象。

验收标准：

- 固定种子可以重现同一局结果。
- 自动运行 1,000 局没有卡死或非法状态。
- 规则测试覆盖移动、碰撞、事件、道具和胜负主要分支。
- 四名参与者可以完成连续多轮行动，暂停、额外行动和胜利不会破坏座次。
- 命令和快照通过 JSON 往返后结果不变；重复或过期命令会被确定性拒绝。

## 3. 里程碑 B：PixiJS 核心体验样片

目标：用最终架构完成一段可玩的高质量流程。

范围：

- 一段约 15 格的临时棋盘。
- 四枚正式风格棋子与四人左上状态列表；其中一名由本地控制，其余使用电脑控制器。
- 开局棋子皮肤选择和至少 4 款皮肤的资源注册。
- 两颗骰子的完整演出。
- 路线延伸、目标圈、路线消失和逐格跳跃移动的完整演出。
- 移动期间的镜头轻推。
- 一次普通落点、一次碰撞和一个事件地标。
- 三张事件卡与一次骰子检定。

验收标准：

- 棋子按状态机给出的路径移动，PixiJS 不修改规则状态。
- 权威规则先提交结果，客户端表现队列再播放动画；动画完成与否不会改变规则结果。
- 骰子定格后严格按照路线绘制、目标圈强调、路线消失、棋子跳跃的顺序播放。
- 棋子逐格跳跃，不允许直接补间或瞬移到目标格。
- 动画完成后状态机能稳定继续，不产生重复回合。
- 1280 x 720 与 1920 x 1080 都保持完整可玩。
- 连续运行 30 分钟不存在明显内存增长。
- 核心体验样片的美术、动画和反馈代表最终质量，不是临时占位表现。

## 4. 里程碑 C：完整棋盘

目标：将核心体验样片扩展为完整的默认 65 格地图对局。

工作内容：

- 制作完整棋盘底图与 66 个固定落点。
- 通过地图清单加载默认地图，并保留注册其他地图与不同格子数量的能力。
- 接入全部地标。
- 完成终点折返动画。
- 完成撞击、保护和交换位置演出。
- 完成全局规则状态提示。
- 接入日志、规则、设置和结算 UI。

验收标准：

- 所有格子坐标有效且不会遮挡关键地标。
- 完整对局可以从选择道具和棋子皮肤持续到胜负结算。
- 重开后场景、状态机、声音接口和定时器全部重置。

## 5. 里程碑 D：内容与电脑玩家

目标：达到首发内容量与基本重复可玩性。

工作内容：

- 扩充到至少 24 张事件和 12 件道具。
- 为事件和道具补齐插画、动画与声音提示 ID。
- 实现基于期望收益的电脑决策。
- 调整事件权重，减少连续重复。
- 自动模拟并分析胜率、平均局长和事件分布。

验收标准：

- 电脑可以正确使用和替换道具。
- 电脑不会因为状态机或动画等待而重复行动。
- 四个座位在大量模拟中的胜率不存在由座次造成的明显失衡。
- 平均单局时长落在 8 至 15 分钟目标内。

## 6. 里程碑 E：表现完善

目标：完成可发布的桌面版本。

工作内容：

- 完成全部场景和 UI 动画。
- 建立 `AudioPort` 与 `NullAudioPort`，接入声音提示调用但不加载音频资源。
- 加入动画速度与镜头运动设置。
- 检查文本溢出、色彩对比和键盘焦点。
- 完成加载、资源失败、页面失焦和恢复处理。

验收标准：

- 1280 x 720、1600 x 900、1920 x 1080 下无重叠和裁切。
- 正常设备上保持接近 60 FPS。
- 首次载入有明确进度反馈，资源失败不会出现空白棋盘。
- 主要流程可以只使用鼠标完成。

## 7. 暂缓项目

以下内容不进入上述里程碑：

- 竖屏、手机端和触屏手势。
- 内容编辑器。
- 账号、匹配、好友和公开大厅。

竖屏和内容编辑器不影响当前架构。账号与大厅暂缓，但在线对局不是取消项：首阶段必须完成协议和 authority 边界，后续按里程碑 F 接入实际传输、房间和恢复流程。

## 8. 明确不做

- 角色属性。
- 角色技能。
- 角色养成、升级和数值成长。
- 棋子皮肤的属性加成、稀有度加成或技能效果。

棋子皮肤只属于外观系统，不为上述角色系统预留规则接口。

## 9. 已确认的实施约束

- PixiJS v8 + XState v5 是正式技术基线，React 继续负责界面层。
- 第 63、64、65 格均为立即获胜的胜利落点。
- 基础 UI 状态、棋盘路线、地标相对位置和风格以指定主参考截图为准。
- 第一阶段只实现桌面横向界面，不考虑竖屏。
- 不建立角色属性、角色技能和养成系统，事件检定只使用骰子。
- 玩家可以在开局时选择纯外观棋子皮肤。
- 移动演出顺序固定为：骰子定格、路线延伸、目标圈强调、路线消失、棋子逐格跳跃。
- 默认地图保留现有 65 格顺序和地标位置；地图系统预留切换地图和改变格子数量的能力。
- 第一阶段只建立声音接口，使用无声音实现，不引入声音资源和播放库。
- 核心体验样片默认选择拾荒沙滩，用于同时验证地标、事件和骰子检定。
- 默认 UI 和离线对局按四名参与者设计，首版由一名本地玩家与三名电脑控制器组成。
- 控制器、规则命令、快照、随机游标和内容版本从里程碑 A 起保持可序列化，不能等联机开发时再改造。
- 玩法扩展通过版本化地图、事件、道具、参与人数和规则集实现；不得以角色属性、技能或养成作为扩展手段。

## 10. 里程碑 F：在线对局

目标：在不修改规则内核和内容定义的前提下，将本地 authority 替换为服务端权威会话。

工作内容：

- 实现私人房间、四个座位的加入/准备/开始和远程控制器。
- 服务端生成随机种子与骰子结果，验证行动权、命令 ID 和 revision。
- 使用快照加增量事件进行同步，支持短时断线重连与表现快进。
- 处理玩家离开、超时和房主转移；具体托管策略在联机实施前单独定案。
- 为客户端版本、规则集版本和内容版本不一致提供明确错误提示。

验收标准：

- 本地、AI、远程玩家可以混合占据四个座位，规则结果与同种子离线局一致。
- 重复、乱序和过期命令不会造成重复投骰、重复移动或重复事件。
- 玩家在任意回合断线重连后能从权威快照恢复，并跳过已经确认的旧动画。
- 任意客户端刷新、动画失败或掉线都不会阻塞其他玩家的权威回合。
