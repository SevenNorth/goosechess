# 实施计划

## 1. 计划用途

本文是可逐项执行的开发清单，不只是产品里程碑。每个阶段必须满足自己的验收命令和退出条件后，才能进入下一阶段。除明确标记为“在线阶段”的任务外，首版必须在不启动后端服务的情况下完成人机对局。

状态约定：

- `[ ]` 尚未开始。
- `[~]` 正在进行。
- `[x]` 已完成并通过本阶段验收。
- `[!]` 被明确问题阻塞，必须在条目后记录原因。

## 2. 当前仓库基线

截至 2026-07-28，仓库实际状态如下：

- 根目录是单包 Vite + React + TypeScript 应用。
- 入口为 `src/main.tsx` 和 `src/App.tsx`，棋盘原型使用 DOM/CSS 绘制。
- 当前脚本为 `npm run dev`、`npm run build`、`npm run test` 和 `npm run preview`。
- 当前只有 Vitest/Testing Library 测试，没有端到端测试。
- 尚未安装 PixiJS、XState、tween.js 或 React Router。
- 尚未建立 `apps/`、`packages/` 或独立游戏服务器。
- `example_screenshots/` 已被 Git 忽略，仅作为本地视觉和玩法参考。

重构原则：保留 Vite 构建方式，把现有单包应用原样迁入 `apps/web`，先保证行为、测试和构建不变，再提取共享规则包。旧 DOM 棋盘暂时作为 `/play` 的实现，直到 PixiJS 核心样片接管；不维护第二套 Web 框架或重复应用。

## 3. 依赖关系与关键路径

```text
阶段 0 基线保护

       └─ 阶段 2 共享包与协议
            └─ 阶段 3 规则内核

阶段 2 至阶段 4 可以先使用无画面的测试驱动开发，但阶段 5 不得绕过已经确定的命令和 authority 接口。阶段 8 不得提前把离线人机模式改成必须连接服务器。

## 6. 阶段 2：共享包与协议骨架

目标：先固定依赖方向和可序列化边界，再编写完整规则。

当前状态：`[x]` 已完成。四个共享包均可独立执行类型检查、测试和构建；协议 JSON 往返与结构化错误测试通过，静态边界检查确认不存在共享包指向应用层的依赖。现有 Web 原型已从 `game-content` 读取事件和道具，完整规则迁移仍按阶段 3 执行。

### 包结构

- [x] 创建 `packages/game-core`：纯类型、随机数、规则函数和 authority reducer。
- [x] 创建 `packages/game-content`：地图、事件、道具、皮肤与规则集配置。
- [x] 创建 `packages/game-ai`：电脑决策策略，只依赖允许公开的规则视图。
- [x] 创建 `packages/game-protocol`：命令、快照、领域事件、表现提示和运行时校验。
- [x] 每个包拥有独立入口、类型检查和测试脚本，不从 `apps/web` 反向导入。

### 依赖约束

- [x] `game-core` 不依赖 React、Vite、PixiJS、XState、DOM、Node.js API 或数据库。
- [x] `game-ai` 只依赖 `game-core` 的公开规则视图和命令类型。
- [x] `game-content` 只提供结构化定义，不包含 UI 组件或任意可执行脚本。
- [x] `game-protocol` 使用 Zod 校验 JSON 输入；协议类型从 schema 推导，避免手写两套结构。
- [x] `apps/web` 负责组合共享包，不能在 UI 中复制规则实现。当前 DOM 原型的旧规则流程仅作为迁移输入保留，不作为共享规则实现。

### 最小协议

- [x] 定义 `GameCommand`、`CommandEnvelope`、`GameSnapshot`、`DomainEvent` 和 `PresentationCue`。
- [x] 定义 `GameAuthorityPort.submit(command)` 与订阅快照/事件的接口。
- [x] 定义稳定的 `gameId`、`playerId`、`commandId`、`revision` 和版本字段。
- [x] 建立 JSON 往返测试，禁止函数、类实例、Map、Set、DOM 或 PixiJS 对象进入快照。
- [x] 对未知命令、未知内容 ID、重复命令和过期 revision 给出结构化错误。

## 8. 阶段 4：离线人机闭环

目标：不用游戏服务器完成 `1v1`、`1v2`、`1v3` 的无画面完整对局和基础准备 UI。

- [ ] 准备界面使用三段选择器，默认选中 `1v1`。
- [ ] 本地控制器将 UI 意图转换为 `GameCommand`。
- [ ] AI 控制器根据合法命令集合、位置、碰撞、道具和事件收益提交同样的 `GameCommand`。
- [ ] AI 随机偏差使用 authority 注入的种子随机源，不直接调用全局随机数。
- [ ] AI 思考延迟只属于客户端表现，不进入规则快照。

### AI 策略

- [ ] 实现事件成功概率与成功/失败收益评分。
- [ ] 实现主动道具使用和新旧道具替换决策。

- [ ] AI 只读取显式公开的 `DecisionView`，不读取未来事件或隐藏随机状态。

### 自动模拟

- [ ] 提供无 UI 模拟入口，可指定模式、局数和种子范围。
- [ ] 每个模式至少自动运行 1,000 局。

- [ ] 检查事件卡长标题、道具说明和参与者名称溢出。
- [ ] 提供动画速度和镜头运动设置。
- [ ] 不实现竖屏布局；低于最低横屏尺寸时给出明确提示。

### 自动化与发布门禁

- [ ] CI 执行安装、类型检查、单元测试、内容校验、构建和关键 E2E。
- [ ] E2E 覆盖 `1v1`、`1v2`、`1v3` 开局和固定种子终局。
- [ ] 为规则快照和协议变更建立显式版本升级检查。
- [ ] 发布构建不包含 `example_screenshots/`、录像、临时帧或调试种子面板。

### 验收

```

退出条件：所有发布门禁通过；目标分辨率无重叠；30 分钟稳定性检查没有持续内存增长；离线模式不发送游戏网络请求。

## 12. 阶段 8：在线对局

目标：在不修改规则内核和内容定义的前提下，将 `LocalAuthority` 替换为独立 Node.js 服务中的 `RoomAuthority`。

详细方案见 [online-multiplayer-plan.md](./online-multiplayer-plan.md)。只有阶段 7 通过后才开始正式在线实现；可以更早做一次受控技术验证，但不得让实验代码进入离线关键路径。

### 前置门禁

- [ ] `game-core`、`game-ai`、`game-protocol` 和 `game-content` 可以在浏览器与 Node.js 中运行。
- [ ] 固定命令序列在 `LocalAuthority` 上可完全重放。
- [ ] 客户端表现队列可以从任意快照重建和跳过旧动画。
- [ ] 协议已经包含 schema、规则集和内容版本。

### 实施顺序

- [ ] 创建 `apps/game-server` 独立 Node.js + TypeScript 常驻服务。
- [ ] 先实现内存房间和两个浏览器窗口的最小地图技术样片。
- [ ] 再实现 2 至 4 个座位、AI 补位、房间准备和完整地图。
- [ ] 服务端独占骰子、事件随机、在线 AI 和最终状态写入。
- [ ] 实现重复/乱序命令处理、快照同步和短时断线恢复。
- [ ] 最后增加持久化、多实例租约、监控和限流。

### 验收

- [ ] 静态 Web 客户端重新部署不影响游戏服务器中的现有房间。
- [ ] 任一客户端动画失败或掉线不阻塞其他客户端的权威回合。
- [ ] 本地和服务端 authority 对相同种子与命令序列产生相同结果。
- [ ] 非当前行动者、伪造骰子结果和版本不兼容命令会被拒绝。

## 13. 每项任务的完成定义

任务只有同时满足以下条件才能标记为 `[x]`：

- 实现符合 `game-design.md`、`technical-design.md` 和 `visual-design.md`。
- 新增或修改的规则拥有对应测试，不能只依靠手工点击。
- 类型检查、相关测试和构建通过。
- 不引入角色属性、角色技能、养成或皮肤规则加成。
- 不把默认地图的 65 格写成共享规则常量。
- 不在 React/PixiJS 组件中直接修改权威规则状态。
- 新依赖有明确用途并锁定版本，没有无理由引入大型框架。
- 文档、命令和实际目录保持一致。
- 工作区不包含参考截图、录像、临时帧、构建产物或本地密钥。

## 14. 暂缓与明确不做

首个离线桌面版本暂缓：

- 竖屏、手机和平板布局。
- 内容编辑器和用户自制内容。
- 账号、好友、公开匹配、排行榜和观战。
- 实际音效、背景音乐和音频播放库。

永久不做：

- 角色属性和属性检定修正。
- 角色技能、等级、经验、装备或养成。
- 棋子皮肤的数值、技能、稀有度或成长加成。

玩法扩展通过版本化地图、格子数量、事件、道具、参与人数和规则集实现，不通过角色系统实现。
